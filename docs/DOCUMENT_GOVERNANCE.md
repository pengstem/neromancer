# 团队协作规范与设计评审清单

本文件将启动会议确立的 **“合作规范四条”** 与 **产品好/坏设计判断标准** 固化下来，供全员与 AI 助手共同遵守。

---

## 一、合作规范四条（工程纪律）

### 1. 代码维持良好 Architecture，绝不滑向“史山”
- 我们鼓励用 AI 提升开发效率，但**不允许把多段无边界逻辑堆在一个文件里**。
- 提交代码前自查：视图层有没有直接写 SQL 或拼 HTTP？有没有复制粘贴大段相似代码？有没有给新函数配清晰注释与单测？发现架构苗头不对，成员之间应直接当场指出并重构。

### 2. 所有“展示性文档”与 `AGENTS.md` 必须人工通读审阅
- **受控文档清单**（修改后必须本人逐字看完才能合入或分享）：
  - `README.md`
  - `AGENTS.md`（AI 读取的指令一旦有偏差，后续写出来的代码会越偏越远）
  - `docs/PRODUCT_CHARTER.md`（项目规划书 / 路演材料）
- **免审草稿区**：AI 在开发具体某个 Feature 时自己生成的 Plan、笔记或中间调试记录（即“左脚踩右脚”文档），统一放在 `docs/dev-plans/`，不作为对外展示材料。
- **核心警告**：**不要把 AI 吐出来的文字原封不动贴出去给队友或评委看！**

### 3. 每个人都写代码
- 有了 AI 辅助和清晰的包分层后，实现单一功能门槛很低。无论原本擅长前端、后端、设计还是策划，都欢迎认领 `FEATURES_BACKLOG.md` 中的小颗粒 Feature 亲手落地。

### 4. 飞书共享文档带 Tag 认领 + 加大功能先对齐
- 大家把想做的 Feature 带 Tag 加到飞书共享文档（同步维护 `docs/FEATURES_BACKLOG.md`）；想加跨模块的大功能前先在群里说一声，全员确认“有必要、不破坏少阻力体验”再动手。
- 这是一个用于学习与打磨设计眼光的项目：如果不小心做出了不合适的功能，随时可以复盘、撤回、当成宝贵的反面教材。

## 二、什么是好设计 vs 坏设计（开发自检清单）

在往界面上多加一个按钮、多加一个弹层之前，请先问自己 4 个问题：

1. **它增加了记录的阻力吗？**  
   - 好设计：先记住再说，哪怕只留下一句语音、一个词、一张照片。  
   - 坏设计：弹出 5 个必填框问用户“所属分类、优先级、标题、预期完成时间”。
2. **它在手机/小窗上好读吗？**  
   - 好设计：彩色记忆球 + 一句像真人在聊天的摘要 + 场景标签；点进去前就知道大概是什么。  
   - 坏设计：满屏挤满密密麻麻的无序文本，或者一串生造缩写。
3. **它把用户最初的想法抹掉了吗？**  
   - 好设计：AI 去重整理目录的同时，右上角「原始证据」一秒听回原音、看回原图。  
   - 坏设计：AI 自动总结完就把用户原话覆盖删除。
4. **这是“在美团里玩游戏”吗？**  
   - 好设计：聚焦捕捉、组织、孵化、酷分享。  
   - 坏设计：在灵感记录本里硬塞论坛评论区、打赏、社交热榜。
